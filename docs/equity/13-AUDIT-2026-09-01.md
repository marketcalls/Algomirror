# Full Audit — 1 September 2026

Commissioned by the product owner: *"review entire flow, process, logics
completely and validate everything done."*

Six independent reviews were run in parallel over the sell path, order
placement, reconciliation and the books, the money arithmetic, alerts and
holdings, and the documents against the code. **Everything below marked
VERIFIED was then re-checked by hand against the source before being written
down.** Findings the reviews reported but that were not independently confirmed
are marked REPORTED and should be treated as leads, not facts.

The headline: the module's *design* holds up well. Its documented rules —
database before broker, never auto-retry an unknown outcome, an unreadable
broker is not an empty one, the broker owns what is held — are real and are
followed almost everywhere. What the audit found is a set of places where the
implementation does not deliver a rule the rest of the code is relying on.

Three of the four defects fixed today were introduced by me earlier the same
day. That is worth stating plainly: the morning's work was tested against
fixtures and against a live sandbox, and it still shipped three faults, one of
which would have been invisible until mid-afternoon.

## CRITICAL — the row lock does not exist

**VERIFIED. FIXED 2 September.** See the closing note at the end of this
section.

`EquityHolding.claim_for_exit` locks the row with `.with_for_update()`, re-checks
the status, sets `EXIT_PENDING` and commits. The whole exit design rests on it —
`09-DESIGN-DECISIONS.md` D3 says so: *"The commit is the exit claim… Two workers
reading a holding of 40 and both selling it leaves the account short."*

This application runs on **SQLite** (`instance/algomirror.db`, WAL mode —
confirmed in step 41's own output). SQLAlchemy's SQLite dialect emits nothing at
all for `FOR UPDATE`; the source reads, in full:

```python
def for_update_clause(self, select, **kw):
    # sqlite has no "FOR UPDATE" AFAICT
    return ""
```

So on this database the claim is an ordinary read-modify-write with **no mutual
exclusion**. Two workers can both read `ACTIVE` and both commit `EXIT_PENDING`.
D3 is true on PostgreSQL and false here.

**What it takes to happen.** The background monitor breaching at the same moment
the operator presses Sell on the same holding. Narrow, but it is the exact event
the claim was written to prevent, and the consequence is selling the position
twice.

**The fix that works on both engines** is to make the claim a conditional
update — `UPDATE … SET exit_status='EXIT_PENDING' WHERE id=? AND exit_status IN
(claimable)` — and treat a row count of zero as "somebody else claimed it".
That is correct on SQLite and on PostgreSQL, and it removes the dependency on a
lock that may or may not be there. It is a contained change to one method, but
it is the load-bearing method in the module, so it should be made deliberately
and tested, not slipped in between two trades.

## CRITICAL — `filled_quantity` is only ever written for a COMPLETED split

**VERIFIED. FIXED 2 September.** See the closing note at the end of this
section.

Across the whole application there is exactly one write:

```
app/models.py:1519                      filled_quantity = db.Column(..., default=0)
app/utils/equity_fill_reconciler.py:691 split.filled_quantity = filled
```

and it sits under `if mapped == EQUITY_SPLIT_STATUS_COMPLETED:`. For a PARTIAL,
CANCELLED or REJECTED split the field stays at zero for ever.

**Why that matters.** Two guards written this afternoon depend on it:

- `_release_rejected_exit` refuses to release when `filled_quantity > 0`,
  because releasing a partly-filled sell would restore shares that were sold.
  Since the field is never written for CANCELLED, that guard never fires.
  A 100-share sell that fills 40 and is then cancelled returns the holding to
  ACTIVE at **100**, when 60 shares exist.
- `_settle_exit_claim`'s PARTIAL branch is unreachable for the same reason. The
  behaviour its docstring describes has never run.

**The fix has an order to it.** Populating `filled_quantity` for every status
must come *with* a check that the broker order is closed before a holding is
released — a PARTIAL split is a live order, and returning the row to ACTIVE
while the remainder is still resting at the broker would re-arm the monitor
against shares already committed to a sell. Fixing the field alone would make
this worse, not better.

## Fixed today

### 1. The holdings sync overwrote a quantity mid-exit — VERIFIED, FIXED

`_sync_holding_rows` has two loops. The second, which zeroes out rows the broker
no longer reports, correctly refuses a row with an exit in flight. **The main
upsert loop had no such check** — and `_settle_exit_claim`, written this morning,
closes a claim by subtracting the filled quantity from `holding.quantity`.

A real broker reduces its holdings the moment a delivery sale fills. So:

> Sell 60 of 100. The broker now reports 40. Refresh the Holdings screen while
> the sell is working — the row is overwritten to 40. The sell completes;
> `remaining = max(40 − 60, 0) = 0`; the holding goes to **EXITED with zero**,
> and **40 shares the user still owns disappear from the application.** On the
> next sync they return as a new position with the stop loss and target cleared.

This is D10a's mistake in a new place: the same sale subtracted twice. It is my
error — I wrote the subtraction this morning on the strength of an invariant
("the sync refuses to touch a row with an exit in flight") that the code only
half implemented.

**Fixed** by making the invariant true: the main loop now skips a row whose exit
is in flight, so the quantity is frozen for the duration and the subtraction is
sound.

### 2. Broker timestamps went wrong every afternoon — VERIFIED, FIXED

This morning's timestamp fix chose between "the broker means IST" and "the
broker means UTC" by asking whether the raw value would be in the future. That
test only works while the event is **less than five and a half hours old**.

Measured, at 13:08 IST:

| Age of fill | Displayed | Correct |
|---|---|---|
| 2 hours | 11:08 | 11:08 |
| 5 hours | 08:08 | 08:08 |
| 6 hours | **12:38** | 07:08 |
| 24 hours | **18:38** | 13:08 |

So a 09:15 trade read correctly all morning and reverted to 14:45 from about
2:45 pm onward. You checked it at 12:26 and it was right; it would have been
wrong by 3:30 pm. A rule that is correct in the morning and wrong in the
afternoon is worse than no rule, because every test run before lunch passes.

The deeper point is that the digits "09:44" are identical whether they are IST
from six hours ago or UTC from half an hour ago. **No arithmetic separates
those.** Only knowing the broker's clock does.

**Fixed** by naming the assumption instead of inferring it: `BROKER_CLOCK_OFFSET`
is IST, stated once, and the conversion is a plain subtraction. Where a
placement time is available it is used as a *sanity check* that logs a warning
on a large disagreement, never as the decision. Verified correct at ages from
six minutes to thirty days.

### 3. The positions merge had no account-disjointness guard — VERIFIED, FIXED

The Order Book and Trade Book mergers both refuse to fold two rows sharing an
account. `_merge_same_position`, written this morning, did not. A broker that
returns a blank product string gives a delivery line and an intraday line on the
same account an identical key — they would fold into one row of 150 shares
listing that account twice, showing a position that can be sold and one that
must be squared off before close as a single line.

**Fixed** and tested: one account can never appear twice in a row, while genuine
multi-account merging is unaffected.

### 4. Half a book counted as a whole one — VERIFIED, FIXED

Both broker readers treated an account as unreadable only when the order book
**and** the trade book refused. If the order book answered and the trade book
did not, the account was reported **verified** with an empty trade list.

> A 100-share buy completes. The order book says COMPLETED, so the split is
> marked filled. Its fills are looked for in an empty trade book and not found.
> COMPLETED is not a chaseable status, so the split is never examined again —
> **the fill is lost permanently**, while the screen asserts the account was
> verified.

**Fixed:** either book refusing now makes the account unreadable, and the log
says which one refused.

## HIGH — reported, not yet verified line by line

These came from the reviews and read as credible. I have confirmed the specific
code shape for the first three; the failure scenarios are theirs.

1. **`modify_order` has no exit awareness.** VERIFIED that it takes
   `total_quantity` from the request with no upper bound, applies no funds check
   and no side check. An exit sell placed by the monitor is an ordinary SELL
   order, so it can be modified to any quantity with none of the holding
   verification that guards every other sell path.
2. **`reference_price` is trusted from the request body.** VERIFIED at
   `routes.py:4598`: the live price is fetched *only when the caller omits the
   field*, despite a comment saying it is resolved server-side rather than
   trusted. It is the sole input to the pre-trade cash check. The shipped screen
   does not send it, so this needs a non-browser client — but it is the only
   money guard before placement.
3. **`not_at_broker` uses `not any(...)`.** VERIFIED at `routes.py:5653`. A
   two-account order where one account's order has vanished from the broker
   reads as fine; the flag only raises when *every* account's order is missing.
4. **`EXIT_PENDING` has no way out.** REPORTED. A crash between the claim and
   the broker call leaves a holding claimed for ever — not monitorable, not
   claimable, not reconcilable (the reconciler finds holdings by `exit_split_id`,
   which is only written after submission), and not clearable from any screen.
   A stale-claim sweeper is the answer.
5. **A GTT exit never settles.** REPORTED. The reconciler skips any split with
   no `broker_order_id`, and a GTT has only a trigger id. Every GTT sell against
   a tracked holding would strand it.
6. **The Order Book's "claimed" set is built from *filtered* orders.** REPORTED.
   Filter to one symbol and your other AlgoMirror orders may reappear as rows
   badged *Placed outside AlgoMirror*.

## Money arithmetic

The charge model itself came through clean. STT both sides, exchange and SEBI on
turnover, stamp duty on buy only, DP on sell only per scrip, and — since this
morning — GST on the service charges including DP but not on STT or stamp duty.
Verified line by line against the statutory treatment.

Four things to know:

1. **A holding with no cost basis shows a fabricated loss.** VERIFIED that the
   flag exists and is never used: `cost_basis_missing` is written at
   `routes.py:1329` and read **nowhere** in any Python, HTML or JavaScript file.
   Where the broker reports a quantity with no average price, Gross P&L is
   correctly suppressed to zero but Est. Costs is not, so Net P&L reads as a
   pure negative — about −₹195 on a 100-share row that has no cost basis at all.
2. **Net P&L can be a paisa off its own stated identity.** The screen says *Net
   = Gross − Est. Costs*. Net is computed from unrounded figures and then
   rounded, while Gross and Est. Costs are rounded separately, so about one row
   in four fails to subtract exactly on screen. Same class of thing between the
   aggregated row and the sum of its per-account expansion.
3. **The funds check omits every buy-side charge.** It compares cash against
   `quantity × price` only. On a ₹1.5 lakh order the charges are about ₹200, so
   an account with ₹1,50,050 passes and is then rejected at the broker.
4. **`_money` uses banker's rounding.** `round(2.675, 2)` gives 2.67 where a
   contract note says 2.68. Always in the same direction for a given value.

None of these move an order. All of them put a figure on screen that a contract
note will not agree with.

## What is sound, and worth saying

The reviews were asked to be adversarial and still reported these as correct:

- **Nothing auto-retries an indeterminate outcome.** Checked end to end — a
  timeout, a dropped connection, an exception and a success with no order id are
  all classified indeterminate; the retry loop stops; the status is terminal;
  the monitor will not touch it; only a human route clears it. D2 holds.
- **The database is written before the broker is called**, on both the buy and
  the sell path.
- **`_broker_holding_counts` never turns "cannot read" into "zero".** Every
  failure mode returns None and no sell is placed.
- **`split_quantity_by_ratio` cannot over-allocate.** Verified by execution
  across ratio sets summing above and below 100.
- **Nothing is ever incremented from broker data.** Quantities are set, and
  fills are guarded by a fingerprint plus a unique database index. Repeated
  reconciliation passes do not inflate anything.
- **Ownership scoping is complete** — every query on every path filters on the
  owning user.
- **The exit monitor's own decision logic** is the best-built thing in the
  module: no stale price, no absurd price, no unknown mode defaulting to
  automatic, one-shot breach markers.
- **API keys** are decrypted on the calling thread, never logged and never
  returned in a payload.

## What I would do next, in order

1. **Decide the database question.** Either move to PostgreSQL or make the claim
   a conditional update. Until then the exit claim is a convention, not a lock.
2. **`filled_quantity` for every status, together with a closed-order check**
   before any holding is released. These two must land as one change.
3. **`modify_order`** — refuse a quantity change on any order backed by an exit
   claim.
4. **A stale-claim sweeper** for `EXIT_PENDING`, and either GTT support on the
   exit path or an outright refusal of GTT there.
5. **The cost-basis flag**, which is already computed and only needs wiring to
   the screen.
6. The rounding and funds-check items, as one pass.

Items 1 and 2 are the ones I would not go live on real money without.

# Both blockers closed — 2 September 2026

## The exit claim no longer depends on a lock that isn't there

`EquityHolding.claim_for_exit` now settles the claim with a **single
conditional UPDATE** and reads the row count as the verdict. Every precondition
is repeated in the WHERE clause — still owned by this user, still in a
claimable status, still carrying no in-flight broker order id, and still
holding the exact quantity and pledge the claim was sized against. One row
updated means this caller took the claim; zero means somebody else did, which
is a normal outcome and not an error.

The row is still read first, but nothing is decided on that read any more — it
exists only to size the claim and to produce a useful refusal message. The
database decides the winner.

Two details that would otherwise bite:

- The UPDATE goes round the ORM, so the in-session copy still holds the
  pre-claim values. It is refreshed before being returned, or the caller would
  read a holding that is EXIT_PENDING in the database and ACTIVE in memory.
- `pledged_quantity` is nullable and a NULL reads as zero everywhere else in
  the class. Only a zero pledge may therefore match NULL; a non-zero pledge
  must match exactly, or a row whose pledge was cleared concurrently would
  satisfy the very claim it should have blocked.

**This was tested, not assumed.** `44_verify_exit_fixes.bat` races two threads
for the same holding on a scratch SQLite database, forty times each way. The
old read-check-write shape is won by **both** racers — the double sell,
reproduced on demand. The new conditional UPDATE is won exactly once, every
time.

The other exit transitions in that block still carry the read-check-write shape
and the decorative `with_for_update()`. They are on the list, but they are not
in the same class of danger: losing a race on a release or a status stamp costs
a redundant write, not a duplicate sell. The comment above the block now says
plainly that the lock does nothing on SQLite, so nobody reads safety into it.

## `filled_quantity` is now written for every status

`_resolve_filled_quantity` replaces the COMPLETED-only branch. Sources, in
order of authority: an explicit filled quantity from the broker; ordered minus
still-pending; everything, when the broker says completed; nothing, when the
broker says rejected. Whatever that yields is then raised to the executions
already on file, because a recorded fill cannot be un-executed by a book that
has not caught up. The result is capped at the ordered quantity.

The important part is what it returns when the broker gives nothing usable:
**None, meaning cannot tell — which is deliberately not zero.** Zero releases a
holding. The field is left untouched rather than being stamped with a figure
that would read as "nothing filled".

## The ordering the audit asked for

The audit said populating the field had to come *with* a closed-order check, or
the fix would make things worse. Both were done together.

**A PARTIAL split is no longer settled.** It used to be in the accepted set,
and that was wrong: a partially filled order is still resting at the broker for
its remainder, and returning the holding to ACTIVE at the reduced quantity
re-arms the stop loss monitor against shares already committed to a sell. Only
COMPLETED, CANCELLED and REJECTED are settled now — the states at which the
broker is finished. A partial fill is settled when the order carrying it
finishes; until then the holding stays claimed, which is the safe place for it.

**A release now needs positive evidence of a clean miss**, not merely the
absence of evidence that shares moved. `filled_quantity` reads zero both when
the broker said nothing filled and when nobody has managed to ask, because the
column defaults to zero. Two further things must now agree: the split has been
read back from the broker at least once (`last_synced_at`), and no execution is
on file for it. Either one failing leaves the holding claimed and logs why. A
stuck holding is recoverable by hand; a holding restored to a quantity that was
already sold is not.
